# تشغيل ترحيل إحالة العميل عبر Email OTP

## الغرض

يحدّث هذا الترحيل إجراء `claim_customer_referral` في Supabase ليعتمد **تأكيد البريد الإلكتروني عبر Email OTP** بدلاً من سجل التحقق الهاتفي الموروث. وهو مطلوب كي يعمل QR الإحالة الخاص بالعميل مع تدفق التسجيل المعتمد حالياً.

يحافظ الترحيل على الحواجز التالية: لا يمكن أن يطالب غير العميل بالإحالة، ولا يمكن للمستخدم إحالة نفسه، ولا يمكن المطالبة بعد أول طلب غير ملغى، ولا يتغير أي سجل قائم عند تطبيق الدالة ذاتها.

## تنفيذ مرة واحدة

افتح SQL Editor في مشروع Supabase الصحيح، ثم انسخ **كامل** محتوى الملف التالي ونفّذه مرة واحدة:

```text
supabase/migrations/20260831_email_otp_referral_binding.sql
```

لا يحتوي هذا الترحيل على `DELETE` أو `UPDATE` للملفات أو الطلبات أو القسائم. وهو يستبدل دالة قاعدة البيانات فقط ويعيد منح صلاحية تنفيذها لدور `authenticated`.

> لا تشارك أي رمز Email OTP أو مفتاح Supabase أو بيانات مستخدم داخل SQL Editor أو المحادثة.

## تحقق آمن بعد التنفيذ

نفّذ استعلام القراءة التالي في SQL Editor. يجب أن تظهر الدالة باسم `claim_customer_referral` ويجب أن تحتوي على السلسلة `EMAIL_OTP_VERIFICATION_REQUIRED`.

```sql
select pg_get_functiondef(p.oid) as function_definition
from pg_proc p
join pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'public'
  and p.proname = 'claim_customer_referral';
```

## اختبار الهاتف اللاحق

افتح رابط إحالة عميل عبر QR على هاتف آخر، ثم أنشئ حساب عميل جديد بواسطة Email OTP. قبل أول طلب غير ملغى، طالب بكود الإحالة وتحقق من قبوله. بعد ذلك، افحص ظهور الإحالة والقسائم وفق دورة الطلب الفعلية؛ لا يُفترض منح مكافأة فورية عند مجرد مسح QR أو إنشاء الحساب.
