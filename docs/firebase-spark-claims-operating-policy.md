# سياسة تشغيل Firebase Custom Claims على خطة Spark

## القرار المعتمد

يعتمد مشروع **سوق الجيران** حالياً الإسناد الإداري اليدوي لمطالبة Firebase Custom Claim التالية لكل مستخدم هاتف جديد:

```json
{ "role": "authenticated" }
```

هذا القرار تشغيلي مؤقت ومقصود. محاولة نشر وظيفة `assignAuthenticatedRoleOnCreate` على مشروع `souq-jiran` أوقفتها Firebase لأن Cloud Functions وArtifact Registry يتطلبان خطة **Blaze**، بينما المشروع على خطة **Spark**.

## الإجراء التشغيلي للمستخدم الجديد

بعد ظهور المستخدم في **Firebase Authentication → Users**، ينفذ المشرف من بيئة Firebase Admin SDK الموثوقة الأمر الموثق في `firebase-custom-claims-guide.md` باستخدام UID الظاهر في Firebase. لا ينفذ هذا الأمر من المتصفح أو APK، ولا تُحفظ مفاتيح خدمة أو كلمات مرور في المستودع.

بعد نجاح الإسناد، ينبغي للمستخدم تجديد Firebase ID token — إما بتسجيل الخروج والدخول من جديد أو بطلب تجديد الرمز من التطبيق — قبل استدعاء أي مسار Supabase يتحقق من مطالبة `role`.

## السجل التشغيلي الأدنى

يحفظ المشرف، خارج ملفات الكود العامة، السجل التالي لكل عملية منجزة:

| الحقل | المطلوب |
|---|---|
| UID | معرف Firebase للمستخدم |
| وقت الإسناد | UTC |
| منفذ العملية | حساب المشرف المصرح |
| نتيجة الأمر | نجاح أو فشل دون رموز حساسة |
| تجديد الرمز | مؤكد أو قيد انتظار المستخدم |

لا يتضمن السجل رقم الهاتف أو كلمة المرور أو رمز SMS.

## التشغيل التلقائي المؤجل

ملفات وظيفة Firebase الجاهزة موجودة في `firebase-functions/`، وتبقى **غير منشورة** إلى أن يقرر مالك المشروع تفعيل خطة Blaze. عندها ينفذ المشرف أمر النشر الموثق في `firebase-automated-claims-implementation.md`، ثم ينشئ مستخدماً اختبارياً للتحقق من الإسناد وتحديث الرمز.

> لا يمثل مسار Spark خللاً أمنياً في ربط Supabase: إجراءات الربط ما زالت تستخرج UID ورقم الهاتف من Firebase JWT الموثوق، لا من مدخلات المتصفح.
